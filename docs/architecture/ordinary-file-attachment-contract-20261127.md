# Ordinary FilesV2 attachment contract

**Status: all 35 component methods and the separate fresh-native attachment method are qualified on Oracle with unchanged source and dependency products. Two original native attachments survived a cold reopen under operating-system network denial. Apple protected-journal and application qualification remain pending.**

The UI owner is Wave 2. The Engine/Host adapter owner is Wave 1. Wave 3 owns final application integration and the native producer. This adapter uses the existing ordinary native file route and does not change the migration API.

## Native operation and identity

The native operation is `POST /v1/spaces/{spaceId}/objects/{objectId}/files`. The body is the original file bytes, not JSON, multipart data, or base64. The `name` query parameter and `Content-Type` header are metadata hints. The original native resolver owns MIME sniffing/refinement and filename extension completion. A successful response is HTTP 201 with the original `FileInfo`: `fileId`, `objectId`, `size`, `inline`, `durable`, `cached`, and optional `rootCid`, `name`, `mime`, `variant`, `variantOf`.

The response does not contain its account or Space. The adapter binds those fields to the original admitted request and validates the returned object, file and byte count. Ordinary attachment creates an original file owned by the existing object; it is available through the object's existing FilesV2 list/query. It does not allocate another object or an editor block. The native engine chooses inline versus content-addressed storage.

The wire surface is present in the original Any `8fbd1e819fb132ac0e0a848d2ddf5c5714189b81` lineage used by the qualified 1594/1599 source products and the later 1607-source content-authority product. Their previous file proofs remain at their original versions and scope. The Swift adapter's component evidence is listed below; the previously exercised native route alone does not qualify this adapter. The content-read guard has its own signed-authority, fresh `Files.Open` and ordinary HTTP evidence. The later metadata/cache-authority correction and shared Apple native producer retain their independent gates.

## Public sequence for the UI

1. Keep security-scoped access to the selected local file while fingerprinting and staging it. Call the bounded local fingerprint helper off the main actor. The helper returns the original byte count and SHA-256; it does not dispatch a native operation.
2. Construct one `AnyNativeFileAttachmentIntent` with the exact `AnyTorahWorkspace`, target object ID, a new 32-character lowercase hexadecimal mutation ID for this user action, metadata hints, byte count and content digest. Preserve this intent for recovery. Reusing its mutation ID with changed content, metadata or target is refused.
3. Obtain the typed service with `try await objects.makeFileAttachmentCreator()` from the existing `AnyNativeObjectCreator` in the document presentation. This factory returns the same attachment-creator actor for the lifetime of its existing object-creator owner. It captures the original client, workspace and existing `AnyNativeCreationJournaling` instance, preserving the private receipt memory across sheet reopenings. It neither opens another journal nor admits a mutation. The explicit creator initializer remains available to the workspace owner with that same journal. Opening a second protected journal owner for the same workspace is not an ownership-transfer mechanism.
4. Call `attach(_:fileURL:authorizeRead:authorizeAttachment:)`. `authorizeRead` is side-effect-free: it checks the active consumer/session, actual account/Space and current read authority. It can be called more than once. `authorizeAttachment` performs fresh write authority and admits the one user mutation. A duplicate call for an already reserved intent cannot consume another native dispatch.
5. Publish the returned attachment only to that still-current UI/session. The result follows native metadata readback, bounded plaintext content verification and another native metadata read. Use its original file reference with the existing durability/status API.

The local fingerprint and private staging copy are two bounded passes. The second pass checks the exact first digest and source identity before dispatch. A changed file is refused before sending. Files range from zero bytes through 512 MiB; larger inputs are explicitly refused by this adapter. The entire file is never loaded into one Swift `Data` value. Ordinary files of both native storage tiers use the same raw-body route.

## Durable ownership and response handling

The adapter extends the existing metadata creation journal with the `fileAttachment` intent kind. The journal retains the scoped mutation identity and its fingerprint, then the original file ID. It does not retain the local source URL, plaintext file, name or MIME hint. One durable reservation owns the permitted POST. The reservation precedes the mutation-approval callback; an approval failure after reservation remains conservatively unresolved and cannot silently acquire a replacement dispatch.

After a valid 201 response, the original-scope receipt callback first retains its actual validated metadata in bounded private memory, then records `.created(fileID)`, before checking the postflight account, consumer lifetime or cancellation. Thus an account change does not redirect the journal write into the newly active account. The client never follows a redirect or obtains a replacement body stream for a replay. Transport interruption, malformed success, a response bound violation, or failure after dispatch ownership has been consumed cannot authorize an automatic resend.

When a later check fails, `AnyNativeFileUploadUncertain.knownReceipt` carries only an `AnyNativeFileUploadAcknowledgement`: the originally scoped file reference and byte count. It does not expose the native name, MIME, root CID or storage state after the lease has failed. Full metadata is confined to the original-scope retention callback and a successfully authorized result. The Host validates the acknowledgement's scope and size before returning its identity-only recovery error.

Native Attach has no established caller-supplied idempotency key. A missing acknowledgement with no known ID cannot be attributed safely by matching filenames or identical content among concurrent uploads. Such a reservation remains unresolved. An explicit native error remains available as a typed status/code, but it is not treated as a rollback receipt and does not erase the reservation.

### Cancellation and transport completion

The Engine keeps ownership of its sole URLSession task, serial delegate queue, continuation and staged file until the exact task's completion callback and the exact session's invalidation callback have both occurred. It queues continuation delivery on that same serial queue after the final callback returns. Cancelling the task and requesting invalidation initiate shutdown; neither call alone proves completion. Session teardown uses `finishTasksAndInvalidate()` after cancelling the sole task so that completion delegates can finish before invalidation.

Task completion and its first outcome are latched under one lock against cancellation. An earlier cancellation remains an uncertain outcome. A completed response latched first is retained for the existing validated-201 callback before the caller's final cancellation and authority checks. Cancellation before registration starts no URLSession or native request. All callbacks remain bound to the original task and session; the operation cannot be reused or redirected.

This barrier lets the existing session owner's joined Swift operation retain its transport and staging resources through their actual delegate completion. It does not claim that cancelling HTTP rolls back a native mutation or proves the native server's work has stopped. The durable reservation and uncertain-outcome rules continue to apply. Apple integration and actual protected-journal close/reopen still require their own acceptance evidence.

The callback contract follows the primary Foundation documentation for [finishing tasks and invalidating a session](https://developer.apple.com/documentation/foundation/urlsession/finishtasksandinvalidate%28%29), [session invalidation callbacks](https://developer.apple.com/documentation/Foundation/URLSessionDelegate/urlSession%28_%3AdidBecomeInvalidWithError%3A%29), and [serial delegate queues](https://developer.apple.com/documentation/foundation/urlsession/init(configuration:delegate:delegatequeue:)). The source review is separate from the actual Linux and Apple runtime receipts.

## Readback and recovery

The successful warm path requires the 201 metadata to agree with the first metadata read. It then reads plaintext content in bounded native HTTP ranges, verifies its complete byte count and original SHA-256, and reads metadata again. Account, Space, object and file identities use exact UTF-8 comparison. The immutable name, MIME, root CID and inline tier must remain stable across the readback. Cache availability and durability may legitimately advance; the final result reports the last actual native observation.

When the original file ID is recorded, `resume(_:authorizeRead:)` performs only metadata/content reads. It does not upload, create a replacement file, or consume another write approval. A new creator using the same durable journal can perform this recovery after a process restart or a lost UI acknowledgement. A recorded reservation without a file ID remains uncertain unless this same owner still has the actual validated acknowledgement; in that case `resume` can record that exact ID and complete readback through an available journal. It never obtains a new dispatch reservation.

### Receipt retention and a poisoned journal

The private memory has a strict limit of 64 unresolved actions. A slot is reserved before journal dispatch ownership and cannot be filled by a caller-supplied file ID. Only the actual validated native 201 callback can retain its full acknowledgement. Unknown or failed actions are not evicted to admit more uploads. A slot is released after the original journal durably records verification, before the final current-authority and original-task cancellation fence. No actor suspension follows that fence. A refusal at final delivery preserves the durable verified ID for later authorized reads.

The original `AnyProtectedCreationJournal` becomes poisoned after an append failure. This adapter does not unpoison, replace or bypass it. A transient custom journal may support a later recording retry, but the protected implementation must pass its existing close/reopen and exclusive ownership rules.

While the original attachment owner and its live account/Space authority still exist, the caller can obtain `retainedRecoveryReceipt(for:authorizeRead:)`. This returns an opaque `AnyNativeFileAttachmentRecoveryReceipt` minted from the actual remembered acknowledgement. It is not Codable, has no public initializer or mutable fields, and redacts its descriptions. The caller cannot reconstruct it from a surfaced ID, a file list or the intent fingerprint. Obtaining it does not query or repair a poisoned journal.

After draining and closing the original session, reopen its original protected journal using the existing namespace, files and lock checks. Construct the new workspace owner with that journal and call `resume(_:recoveryReceipt:authorizeRead:)` with the exact original intent and opaque receipt. The adapter requires an already-existing matching reservation or terminal record, exact scope/fingerprint/byte count, and any already-recorded original file ID. It then records and verifies the same original acknowledgement. An empty journal, changed intent or mismatching known ID is refused; this overload neither reserves a new action nor sends a POST.

The journaling protocol proves the exact scoped identity and state returned by its implementation. Physical continuity of the original protected journal is enforced by the production workspace/session owner and protected-journal opening rules; the protocol alone does not identify a physical file. The in-memory handoff is not cold persistence. If the process exits before the acknowledgement becomes durable, its volatile receipt is lost and a reservation without a known ID remains unresolved.

The caller must preserve the exact bounded Codable `AnyNativeFileAttachmentIntent` separately under the account/Space storage policy. The journal's fingerprint cannot reconstruct it. Wave 2 owns the protected caller-intent storage and UI/session integration; Wave 1 owns the attachment/journal adapter. Neither layer should implement an alternative journal or infer a missing native result.

The journal stores the original file ID and input fingerprint, not the native-normalized 201 metadata. A cold resume therefore proves current stable metadata plus the original content digest. It does not assert that the native metadata has never changed since the initial acknowledgement. Complete historical metadata reconstruction is a different contract.

The low-level `AnyNativeFileUploader` is an Engine transport building block. The UI uses the Host creator so that durable ownership, duplicate suppression and recovery are present for every user action.

## Storage and resource boundaries

The uploader uses an exclusive private directory and regular file, restrictive permissions, no-follow descriptors, one-MiB copy/hash chunks and a bounded 65,536-byte response delegate. Header-declared and chunked response overflow are refused before unbounded accumulation. The original content digest is checked before consuming dispatch ownership. The source descriptor and staging inode/metadata are checked around copying and sending.

Staging is a temporary private plaintext copy, separate from the native engine's encrypted file storage. Apple data-protection and backup-exclusion attributes are applied before staging plaintext on the supported platform. Normal completion removes the owned staging copy. A process crash can leave private temporary residue pending owner/system cleanup; this source implementation does not claim that deferred cleanup has already occurred or that a temporary copy proves cloud custody.

A 201 receipt, successful readback, or cached file is not proof of cloud backup. Inline files are durable by their original native tier semantics. Full-tier files use `AnyNativeFileDurability.status` and the existing explicit `retry` contract. A native storage-limit failure preserves local availability and the original file identity. The UI must not clear the cache or infer upload completion from a retry 204.
