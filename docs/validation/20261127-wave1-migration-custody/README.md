## Custody guarantees

Before copying, both controllers required an exact, closed, exclusively owned
source and a fresh destination with sufficient capacity. They checked process
file descriptors, mappings, executable paths, working directories and command
lines for live consumers; refused special files, unexpected symlinks, nested
mounts and external hard links; and acquired an advisory lock on each source
directory. Reads used `O_NOATIME` and `O_NOFOLLOW`.

The copied bytes were hashed and independently read back after filesystem
synchronization. Portable metadata—mode, UID/GID, access and modification times
in exact integer nanoseconds, extended attributes, and link topology—was
preserved. Original inode, device, change time and allocated size were recorded
and used to detect source replacement; a new filesystem necessarily assigns
new inode/device/change-time values. Source immutability was checked again at
the exchange and retirement barriers.

The original path was exchanged atomically with its verified destination link
using the already qualified `renameat2(RENAME_EXCHANGE)` primitive. The old
bytes were retired only after the stable original path independently resolved
to the verified copy. Exact restoration maps are retained with each receipt.
The controllers never select an unrelated folder or replace an existing
destination. An old controller that requires a *physical* path must receive a
separately reviewed, receipt-bound location successor before reuse; a stable
alias does not automatically satisfy such an admission rule.

The original 182-operation account and private plan, current canonical-eight
proof, and prepared3 manifest remained physical and unchanged. Protected
inputs were checked again in finalization, including on failure. Both custody
controllers refuse optimized Python execution because their acceptance guards
use assertions.
