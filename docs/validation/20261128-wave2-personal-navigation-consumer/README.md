## Problem and behavior

The Host navigation contract was already present, but the actual application owner did not supply it to the library or document lifecycle. This change captures the expected network from the original successful embedded boot, obtains the account/run binding under the existing session lease, and passes one navigation store through the workspace owner, root, library and cached document presentation.

An explicit Home action reads the current preference and validates its destination. Set and unset use the original prepared-intent and acknowledged-write contract. Absent, explicitly empty, object, builtin and unsupported values remain distinct. Personal preferences require current read authority; the original content-edit permissions remain unchanged. Nothing automatically overwrites a restored route or manufactures a Home destination.

The document consumer records a real open only after a current successful read and an actually mounted foreground editor surface. A separate mount identity prevents refresh or repeated activation from creating another open. A true later mount is a new observation. Cached reopen cancels and joins its predecessor before a successor operation, while operation identities prevent old cleanup from clearing newer state.

Prepared intents and synchronous acknowledgments remain available for reconciliation after cancellation or failed postflight readback. They are not automatically resent. The bounded in-memory attempt retention is not presented as a durable journal.

All real canonical boot/binding/contract failures propagate into the existing connection failure and drain path. An optional default only preserves explicitly injected callers; it is not an HTTP 404/501 fallback.

## Foreground correction and retained history

The initial five-file candidate could accept a read while the editor surface was inactive, decline the open correctly, then never reconsider it on ordinary foreground return. The original activation callback only recorded a diagnostic and consumed queued MiniApps results.

The reviewed successor adds one synchronous presentation hook that revisits the same readiness guard, then calls it from the existing activation notification. It does not reset the mount, reload document content, retry an acknowledged write or change MiniApps result consumption. Its extra two insertions are 232 bytes in the presentation and 43 bytes in the view. The final production set is six files and 28 exact literal replacements.

The initial candidate, its blocked review and the corrected source review are retained as historical snapshots. Their then-current runtime/publication holds are not silently rewritten. This source delivery supplies the later W1 donor and completed source reviews; runtime and visual gates remain open.
