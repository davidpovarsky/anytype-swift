## Cancellation and lifetime scope

Canceling a public FIFO waiter neither cancels native work nor retires the process consumer. The helper retains its continuation until the captured accepted frontier is actually delivered or the original consumer ends. The public adapter then performs its existing explicit Task.checkCancellation, so the canceled caller cannot report successful drain. A future closed presentation must retain and join its own close task; this delivery method is only one step after ordinary/native work has truly ceased producing events. It cannot independently prove that future native callbacks are impossible.

The Account handler's original stop path retires its installed registration and cancels any pending registration, with generation/identity checks preventing late adoption. This is not proof that an already-running event callback has drained. The File handler has no original stop path: its installation is process-owned and remains installed across presentation retirement. A canceled startup caller rejects readiness after the shared task finishes; it does not cancel another caller's shared process registration. Per-presentation consumers and frozen forwarding ownership must be retired and drained separately. The unchanged EventBunchSubscriber cancellation still synchronously sets handler=nil; no subscriber rewrite or new event bus is included.
