# Original AccountRecover completion before event-triggered select

The actual native-facing ServiceMessageHandler.handle(Data?) only enqueues to its existing AsyncStream and returns. Its retained consumer later awaits original event handlers. AccountEventHandler.handle sends the original PassthroughSubject synchronously. The existing Login for-await body only assigns UI state; the original LoginView.task(item: accountId) separately schedules selectAccount. The proposed wait is exclusively in that separately scheduled select task. No native callback, FIFO handler or AccountShow receive body awaits the recovery it could otherwise block.

The model registers one retained Task for the actual existing recoverWithOriginalConsumer call before that Task can start on MainActor. The event receiver records the exact current operation reference with its existing accountId assignment. Select checks the same operation/caller reference before and after awaiting that operation's actual throwing completion, and verifies the observed ID did not change. A replaced recovery or retired caller refuses; no later global owner lookup exists. A delayed event can still join its completed current operation because the task receipt remains retained in the model until a later operation replaces it or the model is destroyed.

The original wallet caller's cancellation requests cancellation of this retained Swift task, whose existing Auth/Invocation admission still holds actual native work until return. Select cancellation cannot cancel or manufacture completion of the recovery task: after the actual await, currentness/cancellation is checked before startup. Recovery errors propagate through the existing recovery error path and prevent the event-triggered select from using that failed task. The original Auth parent is inherited unchanged by Task creation; the existing consumer restriction remains in recoverWithOriginalConsumer.

This proposal does not add values, replay, buffering, a second event dispatcher, new auth service or native event provenance. AccountShow's original native account ID remains data validated by the original select route. Only the completion ordering and per-model task identity are strengthened. Actual Combine/SwiftUI/native sequencing still requires Apple qualification.

## Repeated same-account recovery

The original recoverWalletError/accountRecover error paths do not clear accountId. Therefore an identical later AccountShow ID is insufficient by itself to reschedule the original .task(item:) after a failed recovery. Merely setting nil then the same ID is also insufficient if SwiftUI coalesces the intermediate state before a render.

The embedded path now supplies the same existing select task with a tracked UI-only item composed of one immutable UUID belonging to the actual recovery object and the original account ID. It changes for an explicit new recovery even when the native ID is identical, and remains stable for duplicate events from the same observed recovery and ID. The receiver still returns synchronously. At new recovery installation, old event/task-ID state is cleared; the fresh recovery plus subsequent original event supplies the new item. The nil-caller branch continues to pass model.accountId exactly. This scheduling UUID is never passed to Auth, Invocation, native code, the facade, schema or editor authority.

After awaiting recovery.task.value, caller.validateCurrent calls the actual state.validate, whose first statement is Task.checkCancellation. The surrounding actual withUIOperation also validates its original attempt. Select cancellation therefore rejects before original startup even when Swift Task.value itself completes normally. No task creation/yield or cancellation request is treated as actual recovery completion.
