# Exact consumer failure capture

This is an isolated helper proposal. It does not edit the producer driver or run CI. The genuine producer remains the sole owner of launch, timeout, cleanup and acceptance.

1. Before the first English launch, use the existing `command` function to retain successful `xcrun simctl help launch` output under a fresh name, with a 15-second timeout. The helper checks that this actual installed tool advertises both output options. It does not assume a generic tool version supplies them.
2. For each original language/nonce, construct the exact existing 12-element launch argv. Call `prepare_launch_capture(evidence, preflight, installed, original_argv, language, actual_launch_help)`. Use its returned argv in the existing 30-second launch command, with the unchanged `consumer-<language>-launch` command name. Only two output redirection options are inserted. Existing `command` stdout/stderr continue to preserve simctl's own output; the two new files preserve the actual application's output.
3. Wrap the original launch and that language's existing observation validation in `try/except BaseException`. On failure, invoke `[sys.executable, helper_path, '--capture-failure', request_path]` through the existing `command` function, using a fresh `consumer-<language>-failure-capture` name and a 15-second timeout. Record a helper failure separately and re-raise the **original** exception. Do not retry launch, change the primary verdict, publish qualification, or bypass owned cleanup.
4. Run the capture before the existing outer cleanup. The helper owns no subprocess and requests no simulator action. Its parent retains existing POSIX process-group timeout handling. One scan uses a five-second internal budget, 2,048 directory entries maximum, at most eight two-MiB reports, and eight-MiB per output observation. There is no wait for report delivery, recursive search, unified-log collection, host reset or broad crash copy.

Only host `~/Library/Logs/DiagnosticReports` files beginning with the exact executable name are considered. A report must contain the exact consumer bundle identifier, process name, full installed executable path (therefore the owned simulator UDID and app-container identity), and an explicit timestamp in this actual command's time window. The file's own modification timestamp must also fall in that window. Reports without enough native identity fields are not copied. Zero matches means only that this single bounded snapshot found no attributable report.

The request binds current producer/preflight identities and the actual owned iPad name. Actual native `.ips` and text `.crash` parser support remains a diagnostic capability, not a native acceptance assertion. The original error remains authoritative even if diagnostics are unavailable. Application output may still be growing; its hash is expressly an observation at read time, with no implied process drain.

The producer driver's original `command` function and all cleanup/acceptance functions remain unchanged by this isolated proposal. Source review and new meaningful helper-boundary controls are required before integration.
