## Contract and precise scope

The source-bound `operation.go` accepts REPLACE only with source, payload, and
observed physical claim IDs. `projection.go` suppresses exactly those observed
claims and retains independent concurrent successors. The coordinated product
change returns live claims by bytewise **OperationID**, with **Claim.ID** as the
fallback for equal OperationIDs. It does not select one winning successor or
change claim identities, conflict variants, pending references or provenance.

This tail checks that exact tie-break on the received native `Snapshot.Live`.
Every live OperationID is obtained from the actual returned operation and bound
to its canonical bytes, ClaimID and digest before the order is checked. The Go
fixture and Python validator preserve the received list; neither sorts it into
an acceptable order. This does **not** establish causal display ordering from
signed-event ancestry. The combined RFC causal/OperationID acceptance remains
`NOT_PROVEN`; only its explicit bytewise tie-break is addressed here.

Both original native stores first complete the unchanged offline and clean
disconnected-reopen baseline. Two new native OS processes then open those same
stores and verify their original account, native PeerIDs, private ownership,
source pins, and eight-entry signed history. Neither process creates an account,
copies a database, receives a device key, or accepts operation/history bytes
through the controller.

Each process independently reads the actual live predecessor ADD2 through
`PinkhaTorahOperationsReadTarget`, verifies the native signing author against the
original operation, and retains its own returned predecessor claim. Only after
both observations does the controller disconnect B from its owned bridge and
verify the actual attachment on the daemon and the native network state. A writes
REPLACE8 and B writes REPLACE9 through the generated byte entry. Each successor
uses the predecessor's actual target/source and names exactly that claim in
ObservedClaimIDs; the two payloads and operation IDs are distinct.

Before reconnect, each branch must contain exactly nine signed entries: the
unaltered original eight plus its own successor, whose parents are precisely the
two original baseline heads. The other successor must be absent. B must remain
detached after both append receipts. On actual reconnect, native transport must
deliver the exact union of ten signed entries with both successor changes as the
two heads, preserving every original signed-byte hash and parent edge.

The merged projection must contain exactly ADD3 and both successors, in actual
OperationID order (3, 8, 9), with equal semantic snapshot hashes on both peers. It
must retain the complete original conflict4 variant set. Removed original ADD1
and replaced ADD2 must not be live. The successor claims retain their complete
native author, target, source, payload, digest, and exact predecessor reference.
Each phase emits `live_claims` with the same order as `live_claim_ids`, containing
the canonical-validated native claim's OperationID, identity and provenance
hashes. The Python validator requires the exact known ADD2/ADD3 and REPLACE8/9
mapping, checks increasing `(operation_id, claim_id)` pairs, and binds unchanged
ADD3 and successors to their prior native observations. Conflict variant order
continues to use physical ClaimID. The negative controls include correct live
membership in the wrong physical-hash order, including both peers agreeing on
that wrong order; agreement alone cannot make it valid.

After merge each client reconstructs both successor requests from its own
returned native claims and retries them through the generated byte entry. The
actual input SHA256 and length must match the respective first append on its
originating branch. Both clients also retry their own saved predecessor request;
the native receipt must return its original claim unchanged without reviving it.
All retries require AlreadyExistsSamePayload, no ChangeID, and identical complete
read response, local sequence, signed history and head set before/after. These
are retries, not three additional operations.

AccountStop, AppShutdown, read+append denial after stop, matching returned byte
call counters, exactly one named native PASS per process, unchanged original
store/recovery/baseline identities, secret-scanned publication, and existing
owned-resource cleanup are required. The fixed tail work deadline is 600 seconds;
existing bounded native cancellation and cleanup remain separate. No baseline
timeout increases are requested.
