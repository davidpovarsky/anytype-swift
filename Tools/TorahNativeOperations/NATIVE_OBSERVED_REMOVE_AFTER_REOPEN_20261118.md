# Optional native causal REMOVE / re-ADD acceptance

## Scope and existing proof

This is a default-off test tail, authored against Anytype source
`95af681e93662d7e6f0387dc0e59435a1a7edcab`. It adds no production handler,
transport, operation engine, account capability or UI implementation. The five
existing native-client Go fixtures remain byte-identical. The 42 existing native
control terminals and the optional crash profile's 12 terminals remain separate,
unchanged inventories. The normal account/RPC build baseline and the four live
client / disconnected-reopen phases run before this tail.

The existing offline proof already covers same-ID/different-payload conflicts,
concurrent ADD/REMOVE and REMOVE/REMOVE, complete conflict variants, ADD retry,
and two independent disconnected reopens. This addition covers the narrower
gap: identical association content re-added after removal, subsequently removed
by a client that actually observed the new physical claim, and then re-added
again. It also requires exact REMOVE idempotency at both generated byte entries.

## Source-derived author and request identity

`overlay/core/pinkha_torah_operations.go` obtains the signing identity from
`accountservice.Service.Account().SignKey`; `NativeTorahOperationAppend` derives
`AuthorID` from that key. It is not the device's PeerID. The generated append
request contains no author, root, signing key or signed-change bytes.

Each new native session opens its own original root through WalletRecover and
AccountSelect, retains its original PeerID, and reads its actual signing account.
Before writing, it reconstructs the original ID 1 operation with that actual
author and requires both its canonical SHA256 and physical claim ID to equal the
original saved state. The controller independently requires the two actual
authors to agree, while PeerIDs, namespaces, processes and database inodes remain
distinct. It does not infer shared authorship from a shared recovery key alone.

B constructs REMOVE ID 9 from the ID 8 claim in B's own completed Native read.
A independently constructs that same REMOVE from the ID 8 claim retained from
A's earlier completed Native read. Both use the existing generated protobuf
request builder. The test measures SHA256 and length immediately before calling
the real generated `PinkhaTorahOperationsAppend` byte entry. The controller
requires equality across B's original REMOVE, B's retry and A's retry. No encoded
request, operation payload or signed history is passed through host commands.

## Causal sequence on the two original stores

1. Both original accounts have already completed native Stop/Shutdown and their
   disconnected reopen proof. Retire only those stopped owned containers.
   Start two new native processes against the same separate roots on the same
   owned internal LAN. Require the frozen reopen receipts, original recovery
   input hashes, native PeerIDs, account identity and complete eight-change state.
2. A appends operation ID **8** using the exact source, target and payload of
   original ID 1. Its receipt must be CREATED. B must obtain the fresh claim via
   Native ReadTarget and ordinary peer transport. Both readbacks retain the two
   independent live claims and both variants of conflict ID 4; original claim 1
   stays absent.
3. Only after B's read is verified, B appends REMOVE ID **9** naming the observed
   ID 8 claim. Its original response must be CREATED. B immediately retries the
   same encoded request. A first observes the removal through native transport,
   then retries its independently encoded request. Both retries must return
   ALREADY_EXISTS_SAME_PAYLOAD, empty ChangeId and the one exact native REMOVE
   claim, with unchanged full read-response bytes, local sequence and signed
   history. The unrelated live claims and conflict variants remain unchanged.
4. Only after A and B have both proved that removal and retry, A appends operation
   ID **10** with the original association content. B must observe this fresh
   physical claim through native transport. Old claims 1 and 8 remain absent.
   The final native signed history has exactly **11** changes and one head.
5. Both native processes execute AccountStop(removeData:false), AppShutdown, and
   actual post-stop ReadTarget/Append denials. Each exits with one exact named
   Native PASS. The controller's existing owned cleanup and secret-scanned
   publication still gate the overall result.

The first new change joins both original heads; each later change is the sole
child of the previously observed head. Every one of the eight original raw
change hashes and parent lists must remain unchanged. Readiness may wait only
for the immediately preceding fully verified causal state or the existing
strict PROJECTION_BEHIND condition. Unknown heads, missing history, a joined
denial, changed claims or any other error fail immediately. There is no Replay,
history import, AccountCreate fallback, database repair or operation injection.

## Counts, bounds and result interpretation

The new selected Native methods are exactly:

- `TestT2NativeClientObservedRemoveCreatorPhase`
- `TestT2NativeClientObservedRemoveRecoveredPhase`

The original `actual_counts` remain the four baseline client processes / four
named PASS. They are frozen under `completed_offline_baseline` before the
optional tail. The separate `observed_remove_after_reopen` result requires two
new processes, two named PASS, no failures/skips, three new signed operations,
and the eight-to-eleven history transition. A tail failure or cancellation does
not erase the completed baseline and cannot turn the overall run into PASS.

The new host tail has one fixed 600-second deadline. Each new Native test process
has a 720-second outer Go-test ceiling; its work has one 600-second session
deadline, existing bounded byte calls, and bounded native shutdown/denials.
The existing bootstrap, offline, reopen and crash limits are unchanged. The
reusable job retains its existing 60-minute ceiling. Cleanup continues to act
only on the existing recorded owner and exact resource identities.

The six fixed per-role artifact names are `observed-ready.json`,
`observed-added.json`, `observed-removed.json`, `observed-readded.json`,
`observed-final.json` and `observed-remove-native.log`. The existing secret
inventory scans all selected files before publication. Commands, recovery keys,
databases and other private files remain excluded. The source manifest binds
the new Go fixture and Python tail helper in addition to the unchanged original
fixtures and observation patch.
