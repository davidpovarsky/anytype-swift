# T2: two native clients, empty-root LAN bootstrap

## Acceptance boundary

This document describes the default `bootstrap` scenario. The explicit `offline` scenario is documented in [NATIVE_CLIENTS_OFFLINE_20261118.md](NATIVE_CLIENTS_OFFLINE_20261118.md) and retains this entire cold-bootstrap gate before divergent writes.

This lane runs two simultaneous, complete native Anytype applications using the registered T2 generated byte API. Client A creates a fresh synthetic account, Space, Page, block and one private operation. Client B begins with an empty account root and uses `WalletRecover` followed by the native cold `AccountSelect` route. No application capability is enabled.

The host gives B exactly two seed files: the synthetic recovery account key and public expected IDs/hashes. It never copies a database, native device key, saved network port, private signed change, projection, or tree storage. During this bootstrap phase, B does not append private data while its account is active. Both ordinary document access and the original private operation must become readable through the existing native discovery and authenticated peer transport.

An actual `PASS_TWO_NATIVE_CLIENTS_LAN_COLD_BOOTSTRAP` is scoped to this cold bootstrap. It does not prove offline divergent edits and conflict convergence, two iOS applications, or full T2 acceptance. All those fields remain `NOT_RUN`; the App capability remains `OFF`. A passing four-phase baseline is retained separately and cannot substitute for the two-client result.

## Native bootstrap and isolation

The public upstream source at the exact Heart pin was independently checked through unauthenticated GitHub retrieval. `WalletRecover` preserves account identity; a missing native device-key file causes native wallet initialization to generate a new Ed25519 device key and PeerID. `AccountSelect` with an empty root and the original account ID uses native cold recovery; no `AccountCreate`, artificial migration, or database import is needed on B. In LocalOnly mode there are no configured remote nodes. Linux discovery uses the existing `_anytype._tcp` multicast service; the warm peer must already hold the account's technical Space. These are source contracts, not runtime proof that Docker multicast works.

The host creates a uniquely labelled internal Docker bridge. Each client runs the same verified static binary directly as PID 1 in its own network namespace, with its own writable private mount, a read-only root filesystem, a read-only binary mount, and a private `/tmp`. It has no build/source/other-client mount, published port, host PID namespace, privileged mode or capabilities. Both run under the CI user's UID/GID. Each is limited to one CPU, 2 GiB and 256 processes.

Readiness requires the native server to report started, a real nonempty PeerID, the actual bridge address, and a native namespace value matching `/proc/<observed container host PID>/ns/net`. The controller also verifies the exact pinned image, container configuration, owned network membership, different host PIDs, network sandboxes, namespaces, addresses and PeerIDs. After shutdown it requires actual `.db` files under both native account roots and disjoint filesystem device/inode pairs.

Private readiness accepts only the precise original claim and heads. A valid root-only local prefix can wait; unexpected claims, authorization errors or other joined issues fail immediately. Final assertions compare canonical operation bytes and the SHA256 of each original signed tree change, without exporting or injecting the signed changes. B must also perform native `ObjectShow` on the original document with the original name.

## Bounds and shutdown

Every new generated byte call marshals on the test goroutine, invokes the native byte entry point in a worker containing no testing assertions, and returns copied bytes. A fixed call deadline invokes real native `AccountStop` concurrently and allows a bounded 15-second join. A late response after cancellation cannot become success. Cancellation receipts contain method/count/join metadata only, never request, response, account-key or panic content.

The host gives A a total 360-second creation/readiness budget. B has one fixed 540-second budget beginning before seed transfer and container creation; subsequent commands and inspections use the remaining time. A remains alive for up to 600 seconds after its readiness. Once both have proved the original history, the host requests native shutdown and gives both together a 90-second exit budget. The Go executable also has a 1000-second hard test timeout. Existing internal storage calls using `context.Background` are covered by the host deadline and owned-container termination; they are not represented as independently cancellable calls.

A successful phase requires real `AccountStop(false)`, native application closure, subsequent generated read and append returning `NOT_LOGGED_IN`, an exact named test PASS, and exit code zero. Failure, timeout and cancellation never become a synchronized success.

For client resources the controller records ownership intent before a Docker mutation, then checks the exact owner nonce, name and ID before cleanup. It stops/removes only those containers and removes the owned network only when it has no attached containers. Removal is attempted even if native log collection fails. The one-shot SIGTERM/SIGINT handler reaches the existing owned process-group cleanup and final receipt path; repeated signals do not interrupt that cleanup. Any cleanup failure prevents acceptance. The build container uses the existing bounded, disposable `docker run --rm` pattern; it is not either of the two account clients.

## Evidence and interpretation

The build receipt, native-client receipt and existing generation/account receipts bind the same exact source, run and attempt. The actual build must execute all three control methods and all 25 subcases: 28 PASS terminals, no extra test, failure or skip. These comprise the original 13 bootstrap/boundary terminals and 15 controls for offline convergence. The latter controls alone do not prove actual network partition or convergence. The two active clients must produce two further named native phase PASS results. These counts remain distinct from the original four account phases and from Python controller controls.

Only exact allowlisted native metadata and logs can be published. Before creating any native publication directory, the controller scans every candidate against both the synthetic account key and mnemonic. If the creator did not produce a usable secret inventory, all native output is withheld. Raw database files, keys, source overlays, build caches and the executable are never included in the artifact. Docker command logs stay in private work, except the final native logs admitted by this scanner. A secret, unsafe file, unexpected source or cleanup error causes failure rather than a narrowed success claim.

The reusable workflow uploads only `evidence/` for 14 days. It supplies an honest `NOT_RUN_NATIVE_CLIENT_BOOTSTRAP_FAILED` record if an earlier stage prevented the native controller from starting. The parent dispatcher selects this lane explicitly; there is no automatic startup creation, release, deployment, network-service change, or UI matrix.
